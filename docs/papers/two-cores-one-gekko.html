Design study · Draft 1

Two Cores, One Gekko

Splitting the emulation of a single-core GameCube/Wii CPU across two host cores without changing what the guest observes

Dolphin for PS4 projectOctober 2026Status: proposal, no results yet
Abstract

On a base PlayStation 4, the Dolphin port is limited by one host core: the thread that runs the emulated Gekko/Broadway CPU sits at 95–100% load in heavy scenes while the GPU idles at 3–15% and four other cores have spare time. The guest is a single in-order instruction stream, so its work cannot simply be divided. This draft sets out a correctness contract for splitting the emulation anyway, measures how much of the CPU thread's time is not guest code at all, and compares four designs: moving host-side work off the critical thread, a disposable run-ahead helper, speculative parallel execution of guest functions, and decoupled pipelining of hot guest loops. We argue that the first and last are achievable with no change to guest-visible behaviour and estimate their combined ceiling at roughly 1.2–1.4× on the CPU thread; speculation is kept as a research track. An evaluation plan on real hardware closes the paper.

1The bottleneck, measured

The host is the PS4's AMD Jaguar: eight cores at 1.6 GHz (we measured 1,585 MHz), six of them available to applications plus a partly shared seventh. The guest is IBM's Gekko (GameCube, 486 MHz) or Broadway (Wii, 729 MHz), a single-core PowerPC 750 derivative with paired-single floating point. Dolphin translates guest code into host code with its x86-64 JIT and runs it on one thread, the CPU thread. Graphics, Vulkan submission, audio and shader compilation already run on other cores.

The port logs, every two seconds, the emulation speed, the frame rate, each thread's CPU time and the GPU's busy time. A sampling profiler records where the CPU thread spends its time. The numbers below come from those logs.

The pattern is the same in every heavy game: one thread is saturated and everything else waits on it. The question this paper asks is how much of that thread's work could legally happen somewhere else.

What the CPU thread actually does

Profiles split the CPU thread's samples three ways: time in translated guest code, time in Dolphin's host functions, and time in system calls. In Melee's matches about two thirds of the samples land in translated guest code and a sixth in host functions, mostly the hand-over of GPU commands (UpdateGatherPipe, GatherPipeBursted, SetCPStatusFromCPU), translation exceptions and timing. In Crash Bandicoot: The Wrath of Cortex the guest-code share rose from 56% to about 80% after the port's command-stream optimizations removed most of that hand-over cost.

The system-call share in sampled runs is inflated by the profiler's own signals and is excluded from the estimates below.

Write s for the share of the CPU thread's busy time that is not guest code. Amdahl's law bounds what moving all of it elsewhere could gain:

speed-up ≤ 1 / (1 − s)

With s between 0.15 and 0.25 for the games above, offloading host work alone is worth at most 1.18× to 1.33×. Anything beyond that requires executing guest code itself on more than one core, which is the hard part.

2Why the obvious split fails

Cutting the guest's instruction stream in two and running the halves on two cores breaks for five reasons, each of which a design must answer.

  1. Data dependences. Almost every instruction reads a register, condition field or memory location written shortly before. The second core would mostly wait.
  2. Precise exceptions. Games that use the MMU (Spider-Man 2, Call of Duty 2) take data-storage and instruction-storage exceptions at exact instructions. The guest's handler must see the machine as if every earlier instruction completed and no later one started.
  3. Device side effects. Stores to memory-mapped registers (GPU FIFO, DSP mailboxes, video interface, disc controller) take effect immediately and in order. They cannot be repeated, reordered or undone.
  4. Timing. Dolphin counts guest cycles and delivers interrupts and scheduled events (vertical blank, DSP, disc, audio) at block boundaries. Games depend on that order. The port's own speed shortcuts failed in exactly this way: two of them changed when GPU commands became visible and broke three games.
  5. Self-modifying and loaded code. Games load overlays and patch code, and announce it with cache instructions (icbi). Translated code on any core must be invalidated consistently.

3The correctness contract

We call a split transparent if no guest program, and no device, can tell it from the single-threaded emulator. Concretely, at every synchronization point, meaning a device access, an exception, an interrupt check or a block boundary where scheduled events run, the following must hold:

  • the architectural register state equals the single-threaded run's state at the same point;
  • guest memory has the same contents;
  • the device accesses issued so far are the same ones, with the same data, in the same order;
  • the guest cycle count is the same, so events and interrupts fire at the same points.

Between synchronization points the emulator may do anything, including running work on other cores, as long as it restores this picture before the next one. Dolphin's JIT already relies on a weaker form of this: it only checks for interrupts at block exits.

4Four designs

A · Asymmetric decoupling: move everything that isn't guest code

The helper core takes over work the CPU thread does today that the guest cannot observe:

  • Translation. Compile new guest blocks on the helper while the CPU thread runs an existing translation or Dolphin's interpreter, and swap the new code in at a block boundary. Steady-state gain is small, but it removes the stalls when a game enters a new area.
  • GPU command hand-over. The CPU thread only appends bytes to a ring. The helper does the burst copies, write-pointer updates and watermark bookkeeping, and reports back at synchronization points. The port's existing FIFO batching is a first step in this direction.
  • Device models with deferred effects. Audio mixing for high-level DSP emulation, disc reads and controller polling can be computed ahead on the helper and handed over at the guest-visible moment, the same way the video thread already handles GPU work.

Correctness. None of this changes the guest's instruction stream. Each item publishes its results only at a synchronization point, so the contract holds by construction. Gain. Bounded by Section 1 at 1.18–1.33×; we expect a measurable fraction of that.

B · Run-ahead helper

The helper runs a disposable copy of the guest a short distance ahead of the real CPU thread, on a snapshot of registers with writes discarded. Its only job is to make the real thread faster: touch the memory the guest is about to use and translate blocks before the real thread reaches them. Run-ahead execution has been studied in hardware for exactly this reason.

Correctness. Trivially transparent: nothing the helper computes is ever committed. Gain. Unknown. It depends on how often the CPU thread waits on memory, and the Jaguar's 2 MB L2 cache is shared by each group of four cores, so the helper must sit in the same group. The first step is to measure cache misses on the CPU thread before building anything.

C · Speculative function-level parallelism

At a guest function call, core 1 runs the function while core 2 speculatively runs the code after the call, starting from a predicted return state (most PowerPC callers only depend on r3, f1 and the callee-saved registers). Core 2 logs every memory address it reads and buffers every write. When the function returns, the emulator checks that the prediction held and that no address core 2 read was written by the function. If so, the buffered writes commit and the work is kept. If not, it is discarded and redone. A device access, exception or cache instruction on core 2 ends speculation immediately.

Correctness. Transparent if validation is complete, which is the hard part: every guest load and store in speculative code needs instrumentation. Gain. Software thread-level speculation has historically lost much of its benefit to exactly that instrumentation. This is a research track, not a plan.

D · Decoupled pipelining of hot guest loops

Many GameCube engines feed geometry to the GPU with a tight loop: read vertex data, transform or skin it, then write the results to the gather pipe at 0xCC008000. In Crash Bandicoot: The Wrath of Cortex, four such loops took 25–30% of the CPU thread. Such a loop can be cut into two stages connected by a single-producer, single-consumer queue:

Correctness. The split is legal when the loop's dependence graph has no cycle that crosses the two stages: the consumer only performs device writes, and the producer never reads what the consumer writes. Device writes stay in program order, and the queue is drained before the CPU thread reaches any synchronization point, so the contract holds. The port already matches hot loops by their exact code bytes for per-game native replacements, so recognizing candidate loops reuses existing machinery. A general version would derive the split from the JIT's own dependence analysis instead of from per-game patterns.

Gain. Up to the consumer stage's share of the loop's time, minus queue overhead. In vertex-heavy games that share is large, because each gather-pipe write is cheap for the guest but costly to emulate.

5Evaluation plan

Measurements

  • Emulation speed, frame rate and per-thread CPU time from the port's two-second monitor.
  • Per-function and per-guest-routine sample profiles of the CPU thread, before and after each change.
  • Cache-miss counts on the CPU thread, before deciding on design B.

Correctness checks

  • Lock-step comparison. Run the same game twice from the same save state, once single-threaded and once split, with Dolphin's deterministic settings. Record a hash of registers, guest RAM and the device-access log at every vertical blank. Any difference is a bug.
  • Long play sessions on the games that exposed timing faults before (Spider-Man 2, Call of Duty 2: Big Red One, Crash Tag Team Racing, FIFA Street 2), watching for the command-stream errors those games produced.

Milestones

  1. Measure s precisely for five games, separating real host work from profiler artefacts.
  2. Design A, starting with GPU command hand-over and background translation; re-measure.
  3. Design D on Crash Bandicoot: The Wrath of Cortex's vertex loops, then on a second engine.
  4. Decide on B from cache measurements; keep C as a separate research prototype.

6What to expect

A and D together can plausibly take 20–40% off the CPU thread's time in the heaviest scenes measured here, without any change the guest can detect. On Table 1 that is the difference between 85–90% speed and full speed in most of those scenes. It will not turn a 30 FPS game into a 60 FPS one: the game's own frame pacing still applies. General-purpose speculative execution of the guest (design C) is the only route to larger gains, and it remains an open problem in dynamic binary translation.

7Related work

  • Thread-level speculation in hardware: the Multiscalar processor (Sohi, Breach and Vijaykumar, ISCA 1995) and Stanford's Hydra chip multiprocessor, which ran sequential programs speculatively across cores. Design C is a software version of this idea.
  • Decoupled software pipelining (Ottoni, Rangan, Stoler and August, MICRO 2005) splits loops into pipeline stages across threads along an acyclic dependence graph. Design D applies it to translated guest loops.
  • Run-ahead execution (Mutlu et al., HPCA 2003) pre-executes past cache misses to prefetch data, the model for design B.
  • Multi-threaded binary translators such as HQEMU (CGO 2012) move optimization of translated code to helper threads, as design A does for translation.
  • QEMU's multi-threaded TCG runs each guest core on its own host thread. It parallelizes multi-core guests, not a single guest core, which is our case.
